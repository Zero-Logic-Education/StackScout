## Цель

StackScout должен стать не только каталогом библиотек, но и платформой для анализа любых открытых программных артефактов:

- package registries;
- container images;
- repository health;
- security advisories;
- documentation and community signals.

Цель roadmap — расширять домены данных без поломки существующих экранов, API-контрактов и визуального поведения фронтенда.

---

## Принципы развития

1. Добавлять новые источники только через явный контракт и адаптер.
2. Не ломать текущие DTO и текущие экраны при расширении домена.
3. Все новые источники должны поддерживать graceful degradation: нет данных — показываем нейтральное состояние, а не ошибку.
4. Любое изменение источника данных должно сопровождаться тестом и проверкой UI.
5. Фронтенд должен оставаться метадатой-ориентированным: список источников и категорий не должен быть захардкожен в нескольких местах.
6. Новые категории должны вводиться постепенно, без массового рефактора существующего интерфейса.

---

## Текущая база

Сейчас проект уже умеет:

- собирать данные из PyPI и Docker Hub;
- хранить source как строку, а не как жесткий enum;
- запускать сканирование через очереди;
- отображать библиотеки, подписки, обновления и health score;
- администрировать скрейперы и библиотеки.

Ограничение текущей реализации:

- фактически активны только `pypi` и `dockerhub`;
- UI местами предполагает фиксированный список источников;
- сущность `Library` совмещает несколько смыслов, поэтому для новых доменов нужен универсальный слой описания сущностей.

## Этап 1. Унификация источников

### Задача

Сделать единый слой регистрации источников, чтобы новые парсеры подключались без правок в десятке файлов.

### Что нужно добавить

- реестр доступных source adapters;
- единый enum-like descriptor на уровне backend, но с сохранением строкового `source` в БД;
- правила нормализации идентификаторов;
- единый формат ошибок, если source не поддержан.

### Результат

- любой новый источник подключается через один адаптер и одну регистрацию;
- фронтенд получает список источников из API, а не из захардкоженного списка.

## Этап 2. Новые package registry источники

### Приоритет 1

- npm;
- Maven Central;
- NuGet.

### Приоритет 2

- RubyGems;
- crates.io;
- Go modules;
- Packagist.

### Что парсить

Для package registry источников нужно одинаково собирать:

- name;
- version;
- license;
- repository url;
- latest release date;
- description;
- source-specific metadata;
- health score.

### UI-правило

На фронтенде список источников должен строиться из данных API и показываться одинаково, без отдельной логики под каждый registry.

---

## Этап 3. Источники по репозиториям и проектам

### Цель

Добавить источники, которые расширяют StackScout за пределы package registry.

### Кандидаты

- GitHub repositories;
- GitLab repositories;
- Bitbucket repositories;
- GHCR images;
- Quay images;
- Docker registries, совместимые с OCI.

### Что собирать

- stars / forks / watchers;
- contributors;
- release cadence;
- commit activity;
- issues / closed issues;
- last commit time;
- default branch;
- repo visibility;
- image tags and update cadence.

### Польза

Это позволит делать не только анализ пакетов, но и оценку здоровья проекта в целом.

---

## Этап 4. Безопасность и качество

### Источники

- OSV;
- NVD / CVE;
- GitHub Security Advisories;
- dependency vulnerability feeds.

### Что нужно показывать

- количество уязвимостей по severity;
- наличие известных advisory;
- возраст последнего патча;
- trend по уязвимостям;
- объяснение, почему health score снизился.

### Правило UX

Безопасность должна быть объяснима: каждая метрика должна показывать причину, а не только цифру.

---

## Этап 5. Документация и комьюнити-сигналы

### Источники

- README;
- changelog;
- docs site;
- release notes;
- contribution guide;
- issue tracker.

### Что собирать

- наличие и качество документации;
- свежесть changelog;
- frequency of releases;
- активность в issue tracker;
- наличие contribution guidelines;
- support signals.

### Результат

Появится оценка не только «пакет живой или нет», но и «можно ли безопасно его использовать в продукте».

## Правила для frontend и UX

Чтобы frontend не ломался при расширении источников, вводим такие правила:

1. Никаких жестко зашитых списков source в нескольких местах.
2. Все новые типы и источники должны приходить как данные из API.
3. Для неизвестного source должен быть fallback label и fallback icon.
4. Для пустых данных должны быть нейтральные состояния, а не 500 или визуальный мусор.
5. Таблицы и карточки должны адаптироваться к длинным названиям источников.
6. Новые блоки должны появляться без изменения базовой сетки на существующих страницах.
7. Если метрика отсутствует, показываем `—`, а не выдуманное значение.
8. Если новый источник не поддержан в UI, он должен отображаться как generic source, но не ломать страницу.

### UI/UX guardrails

- не добавлять резкие hover-анимации по умолчанию;
- не менять размеры карточек при наведении;
- не увеличивать плотность интерфейса без отдельного решения;
- сохранять понятные empty/error states;
- держать responsive layout для desktop и mobile.

## Технические ограничения и DoD

### Definition of Done для нового источника

- источник добавлен в backend adapter layer;
- источник доступен через API;
- source корректно сохраняется в БД;
- фронтенд показывает его без ошибок;
- для источника есть fallback, если часть метаданных недоступна;
- добавлены тесты backend;
- при необходимости обновлены фронтовые хуки и компоненты;
- в документации описано, какие поля источник предоставляет.

### Что нельзя делать

- не добавлять source только во фронтенд без backend реализации;
- не хардкодить source в одном компоненте и забывать про остальные;
- не ломать существующий путь `pypi` / `dockerhub`;
- не заменять реальные данные заглушками ради простоты отображения.

---

## Критерии готовности релиза

Перед каждым релизом новых источников проверяем:

- backend compile/test проходят;
- frontend lint/build проходят;
- существующие экраны не меняют поведение без причины;
- новые данные не ломают таблицы, графики и фильтры;
- edge cases для пустых/неполных ответов обработаны;
- документация обновлена;
- добавленный источник виден в UI и usable в admin tools.

---

## Рекомендуемая последовательность работ

1. Вынести registry источников и общий контракт адаптера.
2. Добавить npm и Maven Central.
3. Перевести frontend на данные источников из API.
4. Добавить GitHub repository source.
5. Подключить security advisories.
6. Добавить broader project health signals.
7. Перенести модель от Library к более универсальному Artifact/Project view, если появится необходимость.

---

## Итог

Этот roadmap специально сделан так, чтобы проект рос без визуальных регрессий и без рассыпания frontend-контрактов.

Если придерживаться этой очередности, StackScout сможет постепенно перейти от каталога библиотек к полноценной платформе анализа open-source артефактов.
